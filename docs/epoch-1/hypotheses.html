About the project ↗

The hypothesis ledger: predicates the planning model committed to before the data could answer them, each resolved by code. Open a row for the statement, the proposed mechanism and the control that would have shown the mechanism wrong. Below the ledger are the model's readings of the archive and its literature digests.

How to read this

Each row pairs a machine-checkable predicate over per-cell statistics, for example slow.p3s4.heldout < slow.p4s4.heldout, with the mechanism and control the model recorded before the data could answer. p and s name an (order, stages) cell, the leading word picks the cost model, and heldout in a predicate is that cell elite's error on the held-out set, which selects elites and so is not a clean test set.

Verdicts come from code, never from the model. Once every cell a predicate names holds min_samples records, the predicate is evaluated against those cells' running statistics. d is Cohen's d; below 0.2 the verdict is inconclusive whichever way the comparison went, so a weak effect cannot be claimed. A predicate that names an empty cell is inconclusive too, because absence of evidence never refutes. n is the smallest record count among the named cells, and c is the cycle the verdict landed on (c123+ means proposed at cycle 123 and still open).

×N means the model posed that predicate N times over the run. The row shows the newest verdict and lists the id of every posing; mixed beside the verdict means those posings did not all get the same one.

Naive low-precision implementations can lose convergence as the step size decreases, while compensated accumulation and selective higher-precision operations can recover accuracy. Mixed-precision stabilized RK methods further demonstrate that stages serving stability and stages serving accuracy need not use identical arithmetic. For a Q15 implementation with mandatory floor rounding, these results support evaluating each complete arithmetic schedule: floor is biased rather than unbiased, and mitigation operations would consume part of the fixed cycle budget.

Hard-real-time literature continues to favor fixed-step methods because they provide a constant operation count and analyzable worst-case execution time; adaptive schemes introduce variable work unless adaptation and rejection are explicitly bounded. Research on FPGA hardware-in-the-loop simulation likewise evaluates integration methods jointly by stability, model bandwidth, accuracy, and execution time. Consequently, equal-stage RK formulas can have different measured costs because coefficient representation, multiplication, accumulation, reuse, and storage differ; higher formal order does not by itself establish lower cost or lower finite-precision error.

Energy-preserving collocation methods offer a different objective from minimizing trajectory error: for port-Hamiltonian systems they can impose an exact discrete energy-balance relation and retain high formal accuracy, with reported advantages at larger sampling intervals. These methods are generally implicit and therefore bring solve work that is difficult to reconcile with a small fixed cycle allowance. The literature nevertheless suggests adding invariant or energy-drift measurements to held-out evaluation, since a conventional explicit RK method may have small short-horizon state error while introducing undesirable long-horizon energy behavior.

  • Formal RK order is not a reliable proxy for Q15 accuracy under biased floor rounding.
  • Fixed-step execution supports hard deadlines through a constant per-step operation count.
  • Equal stage counts do not imply equal cycle costs because tableau coefficients and dataflow change arithmetic work.
  • Naive reduced precision can destroy expected convergence as steps become smaller.
  • Compensated or mixed-precision operations can improve accuracy but must be charged to the cycle budget.
  • Energy preservation is a distinct quality metric from pointwise or terminal state error.
  • Exact energy-balance collocation is usually implicit, creating potentially substantial and variable solve costs.
